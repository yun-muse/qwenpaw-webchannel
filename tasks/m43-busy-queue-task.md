# M43 — 回答进行中发送新消息：排队 / 立即发送（引导）二选一

用户需求（2026-11-03）：「消息排队机制，在回答的过程中发送新消息要有排队机制，可以选择立刻发送也可以排队，就是现在很常见的引导还是排队这样的功能」。参照主流产品（Claude Code / ChatGPT 等）的 steer（立即发送/引导）vs queue（排队等本轮结束）。

## 探查任务（先查清两件事）

1. **现在的行为**：某会话正在生成中时用户发送新消息——SPA 侧现状（发送按钮禁用？能发？报错？）与插件/QwenPaw 侧现状（同一 session 第二条消息在运行中到达会怎样：排队串行执行？报错？并发？），两侧都给代码证据（SPA 发送路径、QwenPaw executor/session 的并发模型，参考源码 ~/workspace/qwenpaw-ref）。
2. M37 outbox 的状态机与触发信号（轮次结束如何判定：end 帧/收尾 msg；per-chat 的 busy 状态 SPA 现在有没有权威来源），排队功能必须复用这些既有信号，不许另造一套 busy 判定。

## 设计与实现要求

- ** per-chat 忙碌队列**（纯逻辑放 `spa/src/lib/`，可单测）：当该会话有轮次进行中时，用户发送可二选一：
  - **排队**：消息进入忙碌队列，在 composer 上方以队列条呈现（可见、可逐条撤销），当前轮次结束后按 FIFO 逐条自动发出（发一条、等它那轮结束、再发下一条）；
  - **立即发送（引导）**：立刻走正常发送路径发出（其后端行为以探查结论为准——若 QwenPaw 是串行排队执行，UI 文案就如实叫「立即发送」，不许承诺插队效果）。
- **选择 UX**（手机优先，别做复杂）：忙碌时发送按钮旁出现模式切换（或发送时长按/点按小箭头二选一），且有一个记住的默认（localStorage per-user）：用户上次选了什么下次默认什么；不忙碌时不显示这套 UI。文案中文：`排队` / `立即发送`。具体形态由实现方在报告中说明并截图（手机 390px）。
- **边界与一致性**：
  - 队列是 per-chat 的，切会话不串扰；页面重载后忙碌队列如何处理要定义（轮次状态已不可知——建议：重载后队列保留为待发送并在连接恢复且该会话空闲时发出，或转交 outbox 语义，二选一并在报告说明，不许静默丢）；
  - 与 M37 outbox 的关系：断线时发送仍走 outbox（离线优先于忙碌）；忙碌队列中的消息在断线时不许被重复发送，两套队列的去重/衔接写清；
  - 排队消息带附件时：附件待发引用有 10 分钟过期问题（M37 已知）——排队等待可能跨越这个窗口，处理方式要定义（发送时重新校验、过期明确报错并保留文本，还是忙碌排队不支持附件并提示），不许静默丢附件；
  - 停止生成（M42）后：当前轮次结束即应触发队列冲刷（停止也算轮次结束）。
- 若探查发现 QwenPaw 对运行中第二条消息是**直接报错/丢弃**，则「立即发送」在 SPA 侧的真实语义要重新定义并在报告中与协调者确认后再实施（例如立即发送 = 先停止当前轮再发，即「打断重发」语义——这与排队是真二选一）。不许先斩后奏。

## 测试

- vitest：队列纯逻辑（FIFO、撤销、per-chat 隔离、默认模式记忆）。
- Playwright（mock 慢速流）：轮次进行中排队两条 → 本轮结束 → 按序发出且各自回复不串；立即发送 → 在本轮结束前帧已发出（或打断语义下旧轮停止、新轮开始）；排队中撤销一条；切会话隔离；停止后队列冲刷。
