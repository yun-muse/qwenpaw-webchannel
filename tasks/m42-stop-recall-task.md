# M42 — 停止生成修复 + 消息撤回（撤回为探查门控）

用户报告（2026-11-03）：「没有一个撤回的功能，而且在回答的过程中暂停也停不了来，不知道是不是我卡了，需要撤回重发功能，一旦撤回，agent 的回复也要一起撤回」。

## A 部分：停止（暂停）为什么停不了 — bug，必须修好

1. 全链路追踪：SPA 停止按钮（何时可见/可点、流式哪些阶段显示）→ 停止帧 → 插件处理 → QwenPaw 停止 API。仓库 AGENTS.md 已有关键事实：`POST /api/console/chat/stop` 必须传 ChatSpec.id，插件靠 `GET /api/chats?channel=web` + session_id 匹配解析，解析有缓存。逐个环节找失效点，候选（逐一验证或排除，给证据）：
   - 停止按钮在某些流式阶段（思考中/工具调用中）根本不显示或不可点；
   - ChatSpec.id 解析失败/缓存过期（尤其会话刚建立、首轮未落 spec 时）导致 stop 打空；
   - stop 只停了 token 流、停不了正在执行的工具调用，用户观感就是「停不了」（QwenPaw 侧语义要查清并如实记录）；
   - 停止帧的投递被 seq/回放或控制帧规则吞掉。
2. 复现：mock agent 造一个长回复（最好含工具调用阶段），点停止，记录现状行为（帧到没到、流停没停、UI 状态）。
3. 修复后语义：点停止 → 生成在合理时间内停下 → 已生成的部分回复保留并明确标记「已停止」→ composer 立即可用。QwenPaw 语义边界内做不到的部分（如工具调用不可中断）在报告与 UI 文案上如实说明，不许假装全能停。

## B 部分：撤回（含回复一并撤回）— 先探查，有干净路径才做

用户要的语义：撤回自己刚发的消息；若 agent 已在答/已答完，该轮回复一并撤回；撤回的文本回到 composer 可编辑重发（这就是「撤回重发」）。

1. 探查 QwenPaw v2.2.2.post1（参考源码 ~/workspace/qwenpaw-ref + 插件现有调用面）：
   - 是否存在删除消息/截断会话的受支持 API（查 chats/session/history 相关路由与 console 前端自己的调用——console UI 若有删消息/清轮次功能，它调的 API 就是路）；
   - M20 时期对 regenerate/edit 的探查结论是「无受支持的历史改写 API」——这次针对**最后一轮**（最新 user 消息 + 其全部 assistant 回复）重新核：删最后一轮与任意改写历史的难度不同，若有 session 级别的合法手段（如官方的 turn 删除/会话截断/上下文重置接口）在此处记录；
   - Turso 归档侧：撤回后归档如何处理（归档是副本，主历史删了归档要不要同步删——给出一致性方案，搜索还能搜到已撤回内容是不可接受的残留，要么同步处理要么在报告中明确列为残留风险并给出处理）。
2. 判定与实施：
   - **有干净路径** → 实现：入口放在自己消息的操作菜单里（沿用 M26 ⋯ 菜单模式），仅对**最后一轮**开放撤回（非最后一轮涉及历史分叉，明确不在范围并在 UI/报告说明）；生成中撤回 = 先走 A 的停止再删；删除成功后文本回填 composer（不覆盖用户当前草稿——草稿非空时的处理要定义，如追加或提示）；插件/SPA/归档三方一致性按探查方案落地。
   - **无干净路径** → 带证据跳过（同 fork/regenerate 的标准），**严禁用本地隐藏消息冒充撤回**（agent 上下文里还在 = 假撤回）。A 部分照常交付。报告中写清障碍与「QwenPaw 升级后重探」的条件。
3. 协议/插件若需新增帧（如 recall 请求/确认），按现有约定设计并更新 protocol/frames.md；插件改动则构建 ZIP 报大小+MD5（托管安装由 Muse 另行处理）。

## 测试

- A：Playwright 长回复（含工具阶段）点停止 → 流停止、部分回复带已停止标记、composer 可用；插件套件补 stop 解析相关用例（如动了插件）。
- B（若实现）：发消息→等回复完成→撤回→历史与归档搜索均查不到该轮→composer 回填原文；生成中撤回；撤回非最后一轮时入口不存在/被拒。
