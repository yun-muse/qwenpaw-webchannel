# M31 — 附件/图片理解补全（先探查现状，缺哪补哪）

用户视角的目标：像成熟聊天产品一样——发图片能被 agent 看懂、发常见文件能被读取讨论、历史里的附件能回看。本任务先把现状查清，缺什么补什么，不许默认「已经全有了」或「肯定没有」。

## 探查任务（逐项给证据）

1. **发送侧现状**：SPA 现有附件路径（选文件/拖放/粘贴，M22 已接粘贴）支持哪些类型、大小上限（已知 10MB 规则与 chip UI）；帧如何编码附件传给插件（base64 内联？引用？）；插件收到后如何落盘/转交 QwenPaw。引用文件+行号。
2. **QwenPaw 侧能力**：参考源码（~/workspace/qwenpaw-ref）里通道消息的附件/图片表示（content parts？文件引用？）、agent 运行时是否把图片以多模态形式喂给模型、哪些模型路径支持 vision。托管在用的 sensenova/deepseek 系是否多模态——以 QwenPaw 模型元数据/源码证据为准，不许凭印象。
3. **历史侧现状**：带附件的轮次在 hist 帧里如何表示；SPA 历史渲染是否显示附件（图片缩略图/文件 chip）；Turso 归档存不存附件（M15 起归档只有文本？）；导出 Markdown 时附件如何处理。
4. **搜索侧**：全文搜索对附件（文件名）是否可检索。
5. 汇总成「现状矩阵」：发送图片 / 发送文件 / agent 可见性 / 历史回看 / 导出 / 搜索，每格 已支持 / 部分 / 缺失 + 证据。写入 `docs/m31-report.md`。

## 实现任务（只补矩阵里的缺口，按价值排序，能做多少做多少）

候选缺口与预期修法（以探查为准，可调整，但要在报告里说明取舍）：

- 历史里附件不可见 → hist 帧补附件元数据（名称/类型/大小，及图片的可取回路径），SPA 渲染缩略图/chip；
- 图片取回通道：如需新增取文件帧，按现有协议约定设计（控制帧/分块复用 export 的字节数+SHA-256 校验思路），大小上限明确，不许无界传输；
- 导出 Markdown 中附件降级为明确占位（文件名+类型），不静默丢失；
- agent 看不到某类附件且 QwenPaw 无干净路径 → 探查门控跳过，写明障碍（同 fork/regenerate 的处理方式）。

## 约束与测试

- 安全边界：附件取回只能取当前会话归属的文件，路径穿越要有测试用例挡住；类型白名单与大小上限沿用现有规则或在报告里给出新规则的理由。
- 测试：插件套件加附件帧/取回/越界用例；vitest 覆盖渲染判定；Playwright 用 mock agent 跑「发图→历史回看能看到图」全链路（mock 数据即可）。
- 既有套件全绿并报数；涉及插件则构建 ZIP 报大小+MD5（托管安装由 Muse 另行处理，不要动托管环境）。
