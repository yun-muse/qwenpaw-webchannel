# M35 — 附件二期：历史缩略图实装修复 + 一条消息多附件

## 第一部分：缩略图在真实环境不渲染（先查根因）

事实：M31 本地 e2e（mock）里历史图片渲染为缩略图通过；但 2026-10-31 托管真实验收中，上传的 PNG 在历史里只显示为文件 chip（`m31-acceptance.png 179 B`），刷新重开后仍是 chip，没有走缩略图路径。

探查要求：
1. 对比两条数据路径的差异：mock agent 发出的 hist `files` 条目 vs 托管插件对真实 session 文件投影出的 `files` 条目（字段：name/mime/size/kind、URL 去重键、消息归属）。逐项列出真实条目缺了/多了什么——以插件投影代码（`plugin/util.py` 的 hist 投影）+ QwenPaw 真实 session 里附件消息的实际结构为据，引用行号；不许靠猜。
2. SPA 侧判定：缩略图 vs chip 的分支条件是什么（kind==image？mime 前缀？att ref 能否签发？），真实条目在哪一环掉出去。特别注意：att ref 的签发是否只对「当前连接刚上传」的文件有效、而对历史消息里的文件在 hist 时没有重新签发/校验路径。
3. 修复后，e2e 的 fixture 必须**按真实插件的 hist 输出形状**构造（从插件代码/测试里取样，不许再用理想化 mock 形状），并加一条用例断言图片条目渲染为缩略图且 att 取回成功。

## 第二部分：一条消息多附件

探查：发送侧 composer 现在待发附件是单数还是复数（M22 粘贴/拖放路径）；插件组装 QwenPaw 内容时是否支持多个 FileContent/ImageContent；hist 投影与归档、导出对多附件的现状。引用证据。

实现（干净路径存在才做，缺口在哪补哪）：
- composer 可挂多个待发附件（chip 列表逐个可删），一次发送；
- 插件按序组装多附件内容（图片各自配对 ImageContent，规则同 M31 G2-A）；
- 历史多 chip/缩略图渲染、导出多占位、归档文件名列表完整；
- 上限：单消息附件数上限与总大小沿用 10MB 总规则，数量上限在报告里给个数值与理由（如 10 个）。

## 约束

- 安全边界同 M31：att 取回只限本会话归属、media_dir 包含校验不许弱化；路径穿越用例保持。
- 插件若有改动：构建 ZIP 报大小+MD5（托管安装由 Muse 另行处理）。
- 既有套件全绿并报数。报告写 `docs/m35-report.md`：根因（含真实条目与 mock 条目的字段级对比）、多附件探查结论与实现范围、测试结果。
