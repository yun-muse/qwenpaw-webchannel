# M32 — 长对话性能与渲染打磨

背景：产品已日常使用，会话越来越长。成熟聊天产品的流畅度很大一部分死在长对话上：全量渲染几百条消息、流式输出时每个 delta 都触发全量 markdown 重渲染、滚动卡顿。本任务做一次有测量、有对比的性能打磨——**先量后改，用数字说话**，不许凭感觉「优化」。

## 测量任务（先建基线）

1. 用现有 Playwright harness + mock agent 构造长会话 fixture：至少 300 条消息（含代码块、表格、长文本、工具块的混合），记录基线指标：
   - 打开该会话到可交互的耗时；
   - 流式回复期间的长任务/掉帧近似指标（可用 Performance API / CDP 采集 main-thread long tasks 计数与总时长）；
   - 滚动到顶部触发历史加载的耗时；
   - 输入框打字的响应（流式中打字是否卡）。
   测量方法写进 `docs/m32-report.md`，保证改后可同法复测。
2. 定位热点：读 SPA 渲染路径（消息列表组件、markdown 渲染、流式 delta 的 state 更新粒度、代码高亮时机），逐个热点给出代码证据（文件+行号）：全量重渲染？每 delta 重 parse 整个 markdown？高亮在流式中反复跑？布局抖动来源？

## 改进任务（按测量结果取舍，报告里说明每项的收益数字）

候选方向（以证据为准，不要求全做）：

- 历史消息渲染结果缓存/备忘（React.memo 边界、markdown 解析结果按消息内容缓存）；
- 流式期间：增量只渲染尾部、代码高亮延迟到流结束、delta 合并节流（注意不许破坏现有打字机观感与 seq/resume 语义）；
- 超长列表窗口化/分段渲染——**谨慎**：窗口化会与现有「搜索跳到消息（文本锚定）」「滚动恢复」「回到底部」逻辑冲突，若引入必须证明这些功能不回归（既有 Playwright 用例就是裁判）；若冲突过大，改为「首屏渲染最近 N 条 + 向上增量展开」的简单方案；
- 图片/附件懒加载（如 M31 已落地附件渲染，注意衔接）。

## 约束

- 功能零回归是硬线：既有 Playwright 全量（338+）与 vitest 必须全绿；搜索跳转、置顶、草稿、用量收据等既有行为不许变。
- 不许引入大型依赖来「解决」问题（如重型虚拟列表库）除非报告论证收益压倒体积与维护成本，且构建体积增量要报数。
- 交付 `docs/m32-report.md`：基线 vs 改后同口径对比表、每项改动的证据与取舍、未做项及理由。
- 手机视口（390px）下复测一遍主要指标——用户主用手机。
