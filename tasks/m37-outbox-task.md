# M37 — 离线/断线发送队列（Outbox）

背景：手机使用场景下，地铁里断网、agent 正在重启（用户刚经历过多次插件安装重启）、中继抖动时，用户打完字点发送——现在这条消息的命运要先查清。成熟产品（微信/Telegram）的做法是本地排队、恢复后自动发出。本任务给 WebChannel 补上。

## 探查任务（先查现状）

1. 当前发送路径在以下状态的行为，逐个给代码证据与实际后果（消息丢失？报错？假成功？）：
   - WebSocket 未连接/重连中点发送；
   - 已连接但 agent 离线（插件重启窗口期）点发送；
   - 发送途中断线（帧已出、未收到任何回执）。
2. 现有持久化：草稿（M22 per-chat drafts）与 outbox 的边界——草稿是「还没发」，outbox 必须是「已点发送、待送达」，两者不许混。

## 实现要求

- Outbox 纯逻辑放 `spa/src/lib/`（可单测）：per-chat FIFO 队列，localStorage 持久化（键名沿用 `webchannel.` 前缀），条目含本地 id、chat、文本、附件引用状态（如附件尚在待发区，说明与 M35 待发附件如何衔接——附件本体若无法持久化，带附件的消息在离线时如何处理要在报告里明确：是阻止入队并提示，还是仅文本入队，不许静默丢附件）。
- UI：排队中的消息在消息流里以「待发送」形态出现（本地回显必须带待发送标记，**不许伪装成已送达消息**）；可单条撤销；恢复连接且 agent 在线后按序自动发出，发出后本地回显与服务端消息的衔接（去重/替换）要处理好，不许出现双份。
- 触发条件：仅在「连接断开或 agent 离线」时入队；在线时发送失败（如服务端明确拒绝）照旧报错，不许把真失败也吞进队列无限重试。重试上限与放弃策略明确（如随连接恢复最多重试 N 轮，超限保留在队列并标红待用户处理）。
- 与既有机制的兼容：思考等级 pending 补发（M27）、草稿清除时机、seq/resume——逐条说明不冲突的理由；排队消息发出时走**正常发送路径**，不许旁路协议。

## 测试

- vitest：队列纯逻辑（入队/出队/持久化恢复/撤销/上限）。
- Playwright（mock agent）：发消息→杀掉 mock/断开→再发两条（显示待发送）→恢复→断言按序送达且无重复；页面重载后队列仍在并能发出。
- 既有套件全绿并报数。报告 `docs/m37-report.md`：现状行为表、设计、与附件/草稿/effort 的衔接说明、测试结果。
- 纯 SPA 改动优先；若发现必须动协议/插件才能不丢消息，先停下在报告里写清障碍，不要硬改协议。
