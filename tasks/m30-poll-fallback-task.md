# M30 — /poll 降级通道（探查门控，做不出干净方案就带证据跳过）

背景：自 M3 起就挂着的欠账——中继的 `GET /poll` 目前返回 501。设想是给 WebSocket 连不上的网络环境（如某些公司网/代理只放行普通 HTTPS）留一条长轮询降级通道。此项自 M22 规划起就定为**探查门控**：只有能证明干净、不扰动现有 WS 通道的方案才落地；证明不了就写结论跳过，不许硬凑。

## 探查任务（先查后决）

1. relay-cf 现状：`GET /poll` 501 的代码位置、Durable Object 的帧路由/序号/回放（seq + resume 语义）、浏览器侧连接层（SPA 如何建连、断线重连、hb 心跳）在 WS 之外复用的可行性。引用文件+行号。
2. 设计候选并逐条评估：
   - 下行：长轮询拉取（带 last_seq 的 resume 语义必须与 WS 完全一致，不许另 invent 一套序号）；
   - 上行：普通 POST 发送帧（鉴权沿用现有 client token，不许新开无鉴权端点）；
   - 心跳/保活：WS 侧 hb/hb_ack 的等价物在轮询下如何表达；agent 槽位世代（generation-gated slot、close 4000 语义）在轮询下是否还成立。
3. 与 M7.1/M7.3 既有不变量逐条对照（槽位世代、只有槽位持有者被 ack、控制帧不占序号）：轮询方案是否需要改动 relay 的核心状态机？若需要大改，风险收益是否成立？
4. 给出明确结论：**实现**（附设计）或**跳过**（附不可逾越的障碍与证据）。结论写进 `docs/m30-report.md` 的探查部分，由协调者复核后才动代码。

## 若结论为实现

- relay-cf + relay-node 语义保持 lockstep（仓库既有规矩）；SPA 连接层自动降级：WS 建连失败/连续失败达阈值 → 切轮询，UI 有不显眼的降级状态提示；WS 恢复时可切回（切回策略要防抖，不许来回跳）。
- 帧语义零差异：同一测试脚本分别走 WS 与 poll 跑通「发消息→流式回复→resume 补帧」。
- 安全：poll 端点必须走与 WS 相同的 token 鉴权与租户限流口径；报告里写明威胁面变化。
- 测试：relay 两实现各加 poll 冒烟（进 CI 的 relay-node smoke 模式优先）；SPA vitest 覆盖降级判定纯逻辑；Playwright 覆盖强制禁用 WS 时走 poll 完成一轮对话（用现有 mock agent）。

## 若结论为跳过

- `docs/m30-report.md` 写全证据链与「什么条件变化时值得重探」（如 QwenPaw/relay 架构变化）；代码零改动（或仅把 501 的响应体补一句规范说明，如探查认为有价值）。
- 在仓库 AGENTS.md 追加一行：/poll 已探查跳过的结论与重探条件，防止以后重复探查。

## 通用

- 既有套件全绿并报数（插件 pytest、SPA vitest、Playwright、e2e_m29）。CI 路径门控不许动。
