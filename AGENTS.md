# AGENTS.md — qwenpaw-webchannel

Conventions and durable lessons for this repo. Short entries only.

- Chunked M1 work may run as parallel sessions; disk state can contradict what the task brief claims (a brief said `plugin/` was empty while files existed). Always `ls`/read before overwriting, and verify with a real `ls -la` after writing.
- `plugin/util.py` is the only home for the pure helpers (StreamDiffer, SeqCounter, RingBuffer); `plugin/frames.py` re-exports them via the `try: from .util import ... / except ImportError: from util import ...` pattern so both package and top-level plugin-loader imports work. Do not duplicate the logic in frames.py or channel.py.
- `RingBuffer.since(chat, last_seq)` contract: populated buffer → hit list / `[]` when caught up / `None` when `last_seq < oldest-1`; empty buffer → `[]` only when `last_seq == 0`, otherwise `None` (miss → resync; e.g. container restart).
- `approval_frame(chat, req_id, **kw)` — no positional `seq`; pass `seq=...` as a keyword. Reserved keys `t`/`chat`/`req_id` cannot be overridden via `**kw`.
- Plugin tests must not depend on pytest: keep them plain-python assert scripts with a `main()` runner printing `ALL PASS` (pytest optionally collects the `test_*` functions; pytest is not installed in this environment).
- The QwenPaw chat behind a web chat is found with `GET /api/chats?channel=web` + a `session_id` match (`web:web-user:<chat>`), cached per chat in `channel.py`. `POST /api/console/chat/stop` must get that `ChatSpec.id` — its own session fallback is hardcoded to `channel="console"`.
- Approval POSTs need `{"request_id", "session_id": <pending.root_session_id>}`; `session_id` is a required field in `router_approval.py`, and `request_id` alone is a 422. That is why A5 lists `/api/approval/list` first (ownership check + the session id).
- Streaming replies never reach `send()` (base.py consumes the completed message event), so `on_streaming_end` adds the trailing full-text `msg`. Text sent while a stream is open is tool output and must not count as "the answer was delivered".
- `hist` replies use a new `{t:"hist", chat, messages, more?, seq}` frame built by `frames.hist_frame`; they go through `_emit` and therefore consume `seq` (and are replayable on `resume`). Pack them with `util.pack_history` against the `more:true` variant so every frame stays ≤256 KB.
- `E_AUTH` is overloaded: connection-level (no `chat`/`req_id` → stop reconnecting) vs A5 refusing an approve/deny (`chat` + `req_id` → just a card error). Client code must branch on those fields or an approval refusal kills the socket.
- On `resync` the client must forget its per-chat `last_seq`: a container restart restarts `SeqCounter` at 1, so the old high-water mark would filter out the rebuilt history.
- M7 control frames (`models` / `model_changed` / `status`) go out through `channel._send_control` → `relay.send` directly: no `seq`, no ring buffer, no replay on `resume`. Never route them through `_emit`. Raw `ProviderInfo` dicts stay inside the plugin — only `{provider, model, active}` crosses the wire (`util.model_items`).
- M7.1 agent-slot generations: the relay's single agent slot is won at `hello` by `started` (RelayClient construction time, µs) — an older hello is closed 4000 ("superseded") and never evicts the holder, and a RelayClient closed with 4000 treats it as fatal and never reconnects. This is what stops the post-reload replacement war when the old workspace's `stop()` arrives late; do not reintroduce eviction at WS-upgrade time in either relay, and keep relay-node/relay-cf semantics in lockstep.
- M7.2 RelayClient self-healing: each connection phase is supervised (`asyncio.wait(FIRST_COMPLETED)` over reader/writer/heartbeat), sends are time-bounded, WebSocket ping/pong is on, and a supervisor restarts `_run` after any non-fatal exit. Only close 4000, `E_AUTH`, HTTP 401-403 and an explicit `stop()` are fatal — everything else must reconnect. The plugin's `FileLog` (workspace `webchannel.log`, 256 KB × 2 backups) is best-effort by contract: `write()` never raises, so it can never break `start()`.
- M7.3 liveness is `hb`/`hb_ack`, never `ping`: Cloudflare auto-answers `{"t":"ping"}` at the edge (and protocol pings in its front end), so a pong proves nothing about the agent<->DO path. `hb` is acked by the relay process itself, never forwarded, never stamps `agentLastSeen`, costs no bucket token on relay-cf, and only the slot holder is acked (parked generations must stay in the dark). Two consecutive misses end the phase and reconnect. relay-cf and relay-node must keep this in lockstep, and relay-cf deploys first: an old relay broadcasts `hb` to browsers and never acks, so the plugin would reconnect-loop.
- M9 thinking effort: the SPA vocabulary is `default|low|medium|high|max`, and `default` is QwenPaw's `inherit` (always legal, clears the override). Budget models need `{level:"budget",budget_tokens:N}` with `N = round(min+(max-min)*ratio)`, ratios .15/.4/.75/1.0; a bare level is adapted and rejected with 422. Effort models take the exact level only when `control.efforts` lists it. `E_EFFORT` carries `chat`, `status` (404 = no `ChatSpec` yet; the SPA keeps its local choice and retries after the first message) and echoes the request `id`; `effort` is a control frame (no `seq`). The plugin keeps no effort state -- `chat.meta` is the only store.
- M11 persistent login: relay-cf's token TTL is 30 days; the SPA stores the token plus `webchannel.tokenExpires` (Unix seconds) in localStorage and pre-checks it, but the socket stays authoritative. The hosted relay rejects a bad token at the upgrade (browser sees a bare close), so `RelayClient` treats 3 consecutive connects that never opened as an auth failure -- only when the app passed `onAuthFailure` (login builds); local dev keeps retrying. Logout/E_AUTH clear only those two keys.
- M11 usage: `get_usage` / `usage` are control frames (no `seq`, not replayed). `input_total`/`output_total` sum `metadata.qwenpaw_turn_usage.usage` over the chat's assistant messages in `workspace/sessions/web/*.json` (parsed per session id, mtime/size cached); `context_tokens` is the last recorded turn's prompt (`basis=last_turn_prompt`, an approximation) and `context_limit` is `effective_max_input_length`. Unknown fields are omitted, never 0; the handler always answers, at least `{t:"usage",chat}`, and never raises into the chat path.
- M15 usage v2: `hist.messages[]` carries one optional `turn` anchored to the last assistant text segment of each persisted `Msg` (`metadata.original_id`); reasoning/tool splits never carry it, and a group with conflicting usages gets none. A receipt exists only when prompt/completion is usable — no `turn` means "no data", never 0. `usage.last_turn` repeats the newest assistant's receipt (no fallback to an earlier reply). The context numerator is now `last_prompt_tokens` → `context_usage.estimated_tokens` → `prompt_tokens`, because `prompt_tokens` accumulates every model call of a turn and overstates context. The SPA meter sits above the composer (28 px row on mobile, deliberately excluded from the 44 px tap-target audit) and the receipt is the first `.bubble-foot` item (own row on mobile).
- `tests/e2e_m19.mjs` is a self-contained local suite: it runs `npm run build`, starts relay-node on :8787, an in-process mock agent, and `vite preview`. Always pass `--host 127.0.0.1` to preview: Vite binds `::1` by default and `http://127.0.0.1:4173` is refused, while the SPA build's relay URL is baked as `ws://127.0.0.1:8787`. The suite also refuses to start when either port is already taken (a foreign relay would fake a pass).
- Plugin suites need `httpx`, which the system `python3` does not have; run them with `~/workspace/qwenpaw-local/venv/bin/python tests/test_*.py` (that venv also carries the QwenPaw package).
- The SPA's local chat list (`webchannel.chats`) is a union of persisted ids and server ids, never pruned: only the restored *active* chat is validated against the first `chats` frame (M19). Pins (`webchannel.pinnedChats`, newest first) are pruned silently, but only against a non-empty server list — the plugin answers `chats: []` when its own API call fails, so an empty list is not authoritative.
- M22 tap targets: `App.css` has one mobile breakpoint (`max-width: 720px`), so a 44 px rule placed there alone misses coarse-pointer tablets wider than 720 px. Code-block chrome (`.pre-lang` / `.pre-copy`) is gated on `@media (max-width: 720px), (pointer: coarse)`: 44 px bar/button there, 30 px bar and 42×23 button on a fine pointer (desktop look and the Playwright desktop pass). `.pre-lang` gets `padding-right: 72px` so a long language name never slides under 复制. Vite's printed kB is JS string length, not UTF-8 bytes — the CJK UI makes the on-disk file ~8.5 KB larger.
- M24 stats: `get_stats`/`stats` is a control frame (no `seq`, no replay) that never raises; at worst `{"t":"stats"}`. Days are bucketed by the **container-local** calendar day from `Msg.created_at` (naive local wall clock; `finished_at` fallback; offset-aware values converted), a turn with no parseable time counts in the totals but not in `days` (`undated_turns`). `uncovered_chats` = known web chats from `GET /api/chats?channel=web` minus chats with ≥1 usable turn, and is **omitted** (not 0) when that list is unreadable. Top chats are capped at 10 by `input+output`. The scan rides `SessionUsageStore`'s `(mtime_ns, size)` cache; stats totals must equal the per-chat `usage_for` totals (checked against all 37 local session files).
- The e2e mock agent answers `get_stats` from `state.stats` (`DEFAULT_STATS`/`EMPTY_STATS` in `tests/e2e_m19.mjs`), so the dashboard, its jump-to-chat and the empty state are covered in both passes. The M24 tap-target audit is scoped to `.stats-view` on purpose: the M23 toast's compact 关闭 button is asserted ≤24 px elsewhere and may still be on screen behind the overlay.
- M25 bulk export is SPA-only (`spa/src/lib/bulkExport.ts`): it iterates the last non-empty `chats` frame list in server order, one `export` request at a time through the existing M12 frames, and caps the batch at 100 with `skipped` stated in both the panel and the summary. Cancel settles the in-flight job with `已取消` *before* verification can save it, and the runner deliberately does not count an aborted chat as a failure (it is "剩余 N 个未导出"). Failed titles always go to `console.warn` with their reason; the toast names the first three. The button must not reuse `.stats-open` — existing e2e clicks that selector and a second match is a strict-mode failure.
- Fork probe (M25, QwenPaw v2.2.2.post1, `~/workspace/qwenpaw-ref`): no supported way to create a chat seeded with history up to a message. `POST /chats` and `PUT /chats/{id}` are metadata-only (`app/chats/models.py:99-211`), session writes are in-process only (`app/chats/session.py:278`), `POST /console/chat` replays a user turn (`app/routers/console.py:430,498`), and `POST /fork/agent` is a localhost whole-state copy into a `sub-*` subagent session with no ChatSpec (`app/routers/fork.py:44,276-327`). Do not re-probe without a new QwenPaw version.
- Chromium names an `a[download]` file through the **browser process locale**: with `LC_ALL=C` the CJK titles are unrepresentable, the name collapses and Chrome falls back to the literal `download` — downloads still fire, only the name is lost (the anchor's attribute is already correct at click time; the SPA cannot affect this). `tests/e2e_m19.mjs` therefore launches the browser with an explicit UTF-8 locale (`UTF8_LOCALE`/`BROWSER_ENV`) and preflights it (`probeDownloadNames`), so a coordinator shell exporting `LC_ALL=C` cannot turn four M25 filename checks into `["download","download"]`. Reproduce/verify with `LC_ALL=C node tests/e2e_m19.mjs`.
- M26 sidebar: each row has exactly one `.chat-more` (⋯) trigger; the single `.chat-menu` is rendered as a sibling of `.sidebar` (the drawer's CSS `transform` would otherwise re-anchor a fixed bottom sheet) and is a bottom sheet ≤720 px / anchored dropdown otherwise. Tags are intentionally not inline: 46 px mobile / 44 px desktop one-line rows leave no room, so `.chat-menu-tags` plus the 标签 row's trailing `<em>` are the only per-row tag display — do not reintroduce chips there without re-checking the 8-row density target. The M26 evidence block is structure-agnostic and runs before/after the redesign: `M26_ONLY=1 OUT_DIR=./m26-shots/{before,after} node tests/e2e_m19.mjs`; the phone pass is 390×664 (Playwright's iPhone 13), so evidence explicitly `setViewportSize(390, 844)`.
- M27 effort 404: `E_EFFORT` with `status: 404` means only "the `/api/chats` list was readable and this chat has no ChatSpec yet" — an expected pre-creation state, never a toast. The SPA keeps the local level, arms `pending`, and re-applies it **only when a turn completes** (`end` / the closing `msg`), never on send and never on a timer. A failed chat-list lookup must not be reported as 404 (`channel._resolve_chat_id_state` returns a readable flag; `_effort_chat_id` never emits 404 for it), otherwise a cold page load makes existing chats look unborn. `lib/effort.ts::shouldAdoptEffortLevel` stops a differing `get_effort` reply from overwriting a pending choice; a 422/5xx on an existing chat still rolls back and toasts.
- M28 e2e evidence: the mobile theme block runs after the ranking jump, which leaves `chat-beta` active — its mock history (`BETA_HISTORY`) is plain text, while `waitForHistory()` requires `chat-alpha`'s code fence, so a reload restores a page with no `.pre-copy` and times out. It sets `webchannel.activeChat = 'chat-alpha'` before reloading; clicking the sidebar row is not an option because M23.5 leaves `归档专属` in `.chat-search` and the list renders 0 rows.
- M29 PWA freshness: the SW cache name is build-scoped (`webchannel-static-<buildId>`), stamped into `dist/sw.js` from `__WE_CHANNEL_BUILD__` by `serviceWorkerBuildPlugin`. A deploy must change sw.js bytes or `registration.update()` installs nothing. The worker's `activate` owns the cache purge; `version.ts` never deletes caches and reloads only after `controllerchange` (4 s cap). Navigation is network-first with a 5 s timeout; the shell is cached only from a successful navigation under `/index.html` and used only when fetch throws/times out. If you rename hashed assets in an e2e deploy, also rewrite the inlined `__BUILD_ID__` in the bundle — otherwise the "new" page still thinks it is the old build and shows the update banner.
- M29 boot surface: `spa/index.html` carries an inline splash + watchdog (`#boot-splash`, `#boot-watchdog`, no bundle dependency). `App` calls `notifyAppMounted()` (`lib/boot.ts`) on first commit; that removes the node. Script/stylesheet/chunk errors and a 12 s deadline trigger one self-heal (`caches.delete` all + reload). The marker is `webchannel.selfHealAt` in localStorage with a 10 min cooldown, falling back to sessionStorage when storage is blocked; inside the cooldown the splash becomes a 重新加载 card. Keep the watchdog pure HTML/CSS/JS — it is what shows when the bundle cannot load.
- M29 tests: `spa/tests/bootWatchdog.test.ts` runs the actual inline script in `node:vm`; `spa/tests/sw.test.ts` runs `public/sw.js` against fake Cache Storage/fetch/timers; `spa/tests/versionGuard.test.ts` covers the anti-loop decision. `tests/e2e_m29.mjs` builds, serves on :4190 with controllable 503/delay modes, and uses `launchPersistentContext` + close/relaunch to make service workers and Cache Storage survive a real "kill". `M29_LEGACY_DIR=<pre-M29 dist>` reproduces the old white page (purge → reload → one failed bundle request); it is evidence, not a pass/fail regression.
- M30 `/poll` fallback: probed and skipped — the relay is stateless broadcast and control frames are non-replayable by design, so a poll transport would need a second cursor/sequence system in the relay (forbidden) and would negate the DO hibernation cost model. Do not re-probe unless the protocol gains replayable control frames (`seq` or an explicit cursor) or the relay leaves the hibernation model; full evidence in `docs/m30-report.md`.
- M31 attachments: an `image/*` upload must emit **FileContent first, then ImageContent** with the same `file_url` — the FileContent is what makes QwenPaw keep `qwenpaw_original_user_content` (no media-hook "已经下载到 <path>" hint in history/export), the ImageContent is what becomes an `image/*` DataBlock. `_store_file` therefore returns a **list** of parts. `hist` projects `files[]` deduped by URL, keeps attachment-only turns (`text:""`), never publishes a path, and never lets attachments move a `turn` receipt (anchoring is computed on the old text-only `_history_entries`). Retrieval is `att_get` with an opaque `AttachmentRefs` token (10 min, chat-bound) re-validated against a fresh history and `media_dir` (traversal/symlink/oversize → `E_ATT`); `att_*` are control frames like `export_*`. G6 (multi-attachment, accept hint) is deferred. Evidence: `docs/m31-report.md`.
- M32 long-chat perf: the streaming message is the hotspot, not the list. `Markdown` renders a streaming reply as `.md-head` (finished `marked` blocks, HTML cached per token) + `.md-tail` (the growing block) with `display: contents`; settled messages still take the single-pass `renderMarkdown`. Do **not** defer highlighting to stream end: `tests/e2e_m19.mjs:3165` asserts code is highlighted *while it arrives* — the split is how completed blocks stop re-highlighting without breaking that check. `MessageView` is `memo`'d, so its three row callbacks must keep one identity (`rowActionsRef` latest-ref dispatch in `App.tsx`); do not pass fresh closures to it. `tests/perf_m32.mjs` is the measurement harness (`M32_LABEL=before|after`, preview :4191, relay :8787, deterministic 300-message fixture): open is dominated by ~500–600 ms fixed boot (0.3–1.0 ms/message), so long-list windowing was rejected — it would break the `data-mid` scroll in search-jump and only save ~200 ms. Fixtures must stay under relay-node's 256 KB frame cap (600 messages do not fit in one `hist`). Evidence: `docs/m32-report.md`.
- M33 distribution hygiene: plugin-dist (`https://qwenpaw-plugin-dist.pages.dev/webchannel.zip`) is the only plugin ZIP channel. No `*.zip` may be tracked anywhere — the stale `spa/public/webchannel.zip` was removed, the SPA SW no longer special-cases `/webchannel.zip`, and CI job `artifacts` fails on any `git ls-files '*.zip'`. `dist/` stays gitignored: `webchannel.zip` and `webchannel-prev-*.zip` are the local build/rollback flow, never commit them. Evidence: `docs/m33-report.md`.
- M34 backup is SPA-only (`spa/src/lib/zip.ts` + `lib/backup.ts`): a hand-written store-only ZIP (table CRC-32, UTF-8 flag `0x0800`, MS-DOS local time, ZIP32 ceilings 4 GB / 65535 entries) built incrementally — each chat's *verified* `export` bytes become one local header + Blob part, so only the central directory (46 + name per entry) stays in JS and `finish()` is a composite Blob. M25's `planBulk`/`runBulkExport` are reused unchanged; `requestExport(chat, title, deliver)` hands the verified buffer over instead of calling `saveBlob`. Archive names reuse `exportFileName(title, backupStart)` and dedupe with ` (2)` (case-insensitive, `index.md`/`backup.json` reserved); failures come from `BulkRunResult.failed` (never from UI bookkeeping) so they always land in `index.md` + `backup.json` with `filename:null`, and a cancelled run downloads nothing. Message counts are parsed from the export's own `- 消息条数：N` header (first 8 KB), never 0 when absent. `>200 MB` is a modal confirm (unit-tested only: the mock cannot ship 200 MB under the 256 KB frame cap). Sidebar: M26 needs ≥8 full rows at 390×844, so 导出全部 and 备份全部 share ONE 44 px `.bulk-row` (backup label `备份全部` + `.zip` tag, aria-label 备份全部会话) — any extra row or note line drops the list to 7 rows. Evidence: `docs/m34-report.md`.
- M35: the hosted chip-vs-thumbnail bug was `att_get` containment, not the hist projection — the file existed and its size came from `os.stat`, but the one guessed `media_dir` was wrong, `E_ATT` degraded the thumb to a chip. `_media_roots` tries the upload's own parent (learned from `POST /console/upload`'s URL, authoritative), then `console.media_dir` from a one-shot `GET /api/config/channels`, then the old `CONSOLE_MEDIA_DIR`/`<workspace>/media` guess; `media_file_path_in` applies the same `..`/symlink/size rules to each root. The M35 e2e mock mirrors the real projection (`name, kind, mime, size, ref`) and its fixture PNG is 64×64 — dimension checks must read IHDR, not reuse M31's `naturalWidth === 1`. Composer caps (10 files, 10 MB total) live in `attachments.planAttachments`; the rejection text is a separate `attachNotice` because every upload-success path clears `composerError`. Evidence: `docs/m35-report.md`.
