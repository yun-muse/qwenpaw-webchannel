# AGENTS.md — qwenpaw-webchannel

Conventions and durable lessons for this repo. Short entries only.

- Chunked M1 work may run as parallel sessions; disk state can contradict what the task brief claims (a brief said `plugin/` was empty while files existed). Always `ls`/read before overwriting, and verify with a real `ls -la` after writing.
- `plugin/util.py` is the only home for the pure helpers (StreamDiffer, SeqCounter, RingBuffer); `plugin/frames.py` re-exports them via the `try: from .util import ... / except ImportError: from util import ...` pattern so both package and top-level plugin-loader imports work. Do not duplicate the logic in frames.py or channel.py.
- `RingBuffer.since(chat, last_seq)` contract: populated buffer → hit list / `[]` when caught up / `None` when `last_seq < oldest-1`; empty buffer → `[]` only when `last_seq == 0`, otherwise `None` (miss → resync; e.g. container restart).
- `approval_frame(chat, req_id, **kw)` — no positional `seq`; pass `seq=...` as a keyword. Reserved keys `t`/`chat`/`req_id` cannot be overridden via `**kw`.
- Plugin tests must not depend on pytest: keep them plain-python assert scripts with a `main()` runner printing `ALL PASS` (pytest optionally collects the `test_*` functions; pytest is not installed in this environment).
- The QwenPaw chat behind a web chat is found with `GET /api/chats?channel=web` + a `session_id` match (`web:web-user:<chat>`), cached per chat in `channel.py`. `POST /api/console/chat/stop` must get that `ChatSpec.id` — its own session fallback is hardcoded to `channel="console"`.
- Approval POSTs need `{"request_id", "session_id": <pending.root_session_id>}`; `session_id` is a required field in `router_approval.py`, and `request_id` alone is a 422. That is why A5 lists `/api/approval/list` first (ownership check + the session id).
- Streaming replies never reach `send()` (base.py consumes the completed message event), so `on_streaming_end` adds the trailing full-text `msg`. Text sent while a stream is open is tool output and must not count as "the answer was delivered".
- `hist` replies use a new `{t:"hist", chat, messages, more?, seq}` frame built by `frames.hist_frame`; they go through `_emit` and therefore consume `seq` (and are replayable on `resume`). Pack them with `util.pack_history` against the `more:true` variant so every frame stays ≤256 KB.
- `E_AUTH` is overloaded: connection-level (no `chat`/`req_id` → stop reconnecting) vs A5 refusing an approve/deny (`chat` + `req_id` → just a card error). Client code must branch on those fields or an approval refusal kills the socket.
- On `resync` the client must forget its per-chat `last_seq`: a container restart restarts `SeqCounter` at 1, so the old high-water mark would filter out the rebuilt history.
- M7 control frames (`models` / `model_changed` / `status`) go out through `channel._send_control` → `relay.send` directly: no `seq`, no ring buffer, no replay on `resume`. Never route them through `_emit`. Raw `ProviderInfo` dicts stay inside the plugin — only `{provider, model, active}` crosses the wire (`util.model_items`).
- M7.1 agent-slot generations: the relay's single agent slot is won at `hello` by `started` (RelayClient construction time, µs) — an older hello is closed 4000 ("superseded") and never evicts the holder, and a RelayClient closed with 4000 treats it as fatal and never reconnects. This is what stops the post-reload replacement war when the old workspace's `stop()` arrives late; do not reintroduce eviction at WS-upgrade time in either relay, and keep relay-node/relay-cf semantics in lockstep.
- M7.2 RelayClient self-healing: each connection phase is supervised (`asyncio.wait(FIRST_COMPLETED)` over reader/writer/heartbeat), sends are time-bounded, WebSocket ping/pong is on, and a supervisor restarts `_run` after any non-fatal exit. Only close 4000, `E_AUTH`, HTTP 401-403 and an explicit `stop()` are fatal — everything else must reconnect. The plugin's `FileLog` (workspace `webchannel.log`, 256 KB × 2 backups) is best-effort by contract: `write()` never raises, so it can never break `start()`.
- M7.3 liveness is `hb`/`hb_ack`, never `ping`: Cloudflare auto-answers `{"t":"ping"}` at the edge (and protocol pings in its front end), so a pong proves nothing about the agent<->DO path. `hb` is acked by the relay process itself, never forwarded, never stamps `agentLastSeen`, costs no bucket token on relay-cf, and only the slot holder is acked (parked generations must stay in the dark). Two consecutive misses end the phase and reconnect. relay-cf and relay-node must keep this in lockstep, and relay-cf deploys first: an old relay broadcasts `hb` to browsers and never acks, so the plugin would reconnect-loop.
- M9 thinking effort: the SPA vocabulary is `default|low|medium|high|max`, and `default` is QwenPaw's `inherit` (always legal, clears the override). Budget models need `{level:"budget",budget_tokens:N}` with `N = round(min+(max-min)*ratio)`, ratios .15/.4/.75/1.0; a bare level is adapted and rejected with 422. Effort models take the exact level only when `control.efforts` lists it. `E_EFFORT` carries `chat`, `status` (404 = no `ChatSpec` yet; the SPA keeps its local choice and retries after the first message) and echoes the request `id`; `effort` is a control frame (no `seq`). The plugin keeps no effort state -- `chat.meta` is the only store.
- M11 persistent login: relay-cf's token TTL is 30 days; the SPA stores the token plus `webchannel.tokenExpires` (Unix seconds) in localStorage and pre-checks it, but the socket stays authoritative. The hosted relay rejects a bad token at the upgrade (browser sees a bare close), so `RelayClient` treats 3 consecutive connects that never opened as an auth failure -- only when the app passed `onAuthFailure` (login builds); local dev keeps retrying. Logout/E_AUTH clear only those two keys.
- M11 usage: `get_usage` / `usage` are control frames (no `seq`, not replayed). `input_total`/`output_total` sum `metadata.qwenpaw_turn_usage.usage` over the chat's assistant messages in `workspace/sessions/web/*.json` (parsed per session id, mtime/size cached); `context_tokens` is the last recorded turn's prompt (`basis=last_turn_prompt`, an approximation) and `context_limit` is `effective_max_input_length`. Unknown fields are omitted, never 0; the handler always answers, at least `{t:"usage",chat}`, and never raises into the chat path.
- M15 usage v2: `hist.messages[]` carries one optional `turn` anchored to the last assistant text segment of each persisted `Msg` (`metadata.original_id`); reasoning/tool splits never carry it, and a group with conflicting usages gets none. A receipt exists only when prompt/completion is usable — no `turn` means "no data", never 0. `usage.last_turn` repeats the newest assistant's receipt (no fallback to an earlier reply). The context numerator is now `last_prompt_tokens` → `context_usage.estimated_tokens` → `prompt_tokens`, because `prompt_tokens` accumulates every model call of a turn and overstates context. The SPA meter sits above the composer (28 px row on mobile, deliberately excluded from the 44 px tap-target audit) and the receipt is the first `.bubble-foot` item (own row on mobile).
- `tests/e2e_m19.mjs` is a self-contained local suite: it runs `npm run build`, starts relay-node on :8787, an in-process mock agent, and `vite preview`. Always pass `--host 127.0.0.1` to preview: Vite binds `::1` by default and `http://127.0.0.1:4173` is refused, while the SPA build's relay URL is baked as `ws://127.0.0.1:8787`. The suite also refuses to start when either port is already taken (a foreign relay would fake a pass).
- Plugin suites need `httpx`, which the system `python3` does not have; run them with `~/workspace/qwenpaw-local/venv/bin/python tests/test_*.py` (that venv also carries the QwenPaw package).
- The SPA's local chat list (`webchannel.chats`) is a union of persisted ids and server ids, never pruned: only the restored *active* chat is validated against the first `chats` frame (M19). Pins (`webchannel.pinnedChats`, newest first) are pruned silently, but only against a non-empty server list — the plugin answers `chats: []` when its own API call fails, so an empty list is not authoritative.
- M22 tap targets: `App.css` has one mobile breakpoint (`max-width: 720px`), so a 44 px rule placed there alone misses coarse-pointer tablets wider than 720 px. Code-block chrome (`.pre-lang` / `.pre-copy`) is gated on `@media (max-width: 720px), (pointer: coarse)`: 44 px bar/button there, 30 px bar and 42×23 button on a fine pointer (desktop look and the Playwright desktop pass). `.pre-lang` gets `padding-right: 72px` so a long language name never slides under 复制. Vite's printed kB is JS string length, not UTF-8 bytes — the CJK UI makes the on-disk file ~8.5 KB larger.
- M24 stats: `get_stats`/`stats` is a control frame (no `seq`, no replay) that never raises; at worst `{"t":"stats"}`. Days are bucketed by the **container-local** calendar day from `Msg.created_at` (naive local wall clock; `finished_at` fallback; offset-aware values converted), a turn with no parseable time counts in the totals but not in `days` (`undated_turns`). `uncovered_chats` = known web chats from `GET /api/chats?channel=web` minus chats with ≥1 usable turn, and is **omitted** (not 0) when that list is unreadable. Top chats are capped at 10 by `input+output`. The scan rides `SessionUsageStore`'s `(mtime_ns, size)` cache; stats totals must equal the per-chat `usage_for` totals (checked against all 37 local session files).
- The e2e mock agent answers `get_stats` from `state.stats` (`DEFAULT_STATS`/`EMPTY_STATS` in `tests/e2e_m19.mjs`), so the dashboard, its jump-to-chat and the empty state are covered in both passes. The M24 tap-target audit is scoped to `.stats-view` on purpose: the M23 toast's compact 关闭 button is asserted ≤24 px elsewhere and may still be on screen behind the overlay.
