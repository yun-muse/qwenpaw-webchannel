# M7.3 findings — end-to-end heartbeat: the masking mechanism, proven by reading the relay

## The incident (hosted, 2026-10-27 evening, after the M7.2 deploy)

- 20:42 and 21:12 CST soak probes: status-frame timeout while the relay's
  `/health` still reported `agentOnline: true`.
- 21:19 CST discriminating probe that skipped the status wait: the `models`
  request also timed out. **No frame flowed in either direction.**
- The plugin's `webchannel.log` has **nothing** at any of those times: the last
  `hello` is 21:03, and there is no `phase_end`, `close`, `reconnect` or
  `fatal` line afterwards. The plugin believed it was connected.
- Earlier that evening the same log **did** show `phase_end reader` +
  `close code=1006` + `reconnect` (20:11–20:28, 21:02–21:03): M7.2's supervisor
  works whenever the death is noisy. This death was **silent** — no RST ever
  reached the plugin.

## The hypothesis, checked against the code

> The relay answers `{"t":"ping"}` at the edge without waking the Durable
> Object, and Cloudflare also answers WebSocket-level pings. Therefore neither
> app-level `pong` nor WS ping/pong can detect a dead agent ↔ DO path, and
> M7.2's supervisor (which only reacts to a *phase end*) has nothing to react
> to.

**Verdict: confirmed.** The pieces, each read from this tree:

1. `relay-cf/src/index.ts` — the `RelayDO` constructor installs
   `setWebSocketAutoResponse(new WebSocketRequestResponsePair('{"t":"ping"}', '{"t":"pong"}'))`.
   The platform answers that exact text itself; the object is never woken, so
   `webSocketMessage` — and with it the `ping` branch there — never runs
   for it.
2. WebSocket-level (protocol) pings are terminated in Cloudflare's WebSocket
   front end, not by the Durable Object. The plugin's `websockets` keepalive
   (`ping_interval=20`, `ping_timeout=20`) therefore also measures the
   container ↔ edge path, not the container ↔ object path. On relay-node the
   same keepalive *is* end-to-end, which is why local silence tests pass and
   the hosted deployment still froze (M7.2 findings, hole H4).
3. M7.2's supervisor restarts `_run` after a phase ends, and a phase ends when
   one of {reader, writer, heartbeat} ends. A half-open tunnel leaves all
   three parked: the reader sits in `ws.recv()`, the writer waits on an empty
   queue, and the heartbeat **received its pong** (the edge sent it), so it
   timed out on nothing and looped forever. No phase end, no supervisor, no log
   line.
4. The incident log is the corroboration: had the app-level pong *not* come
   back, M7.2 would have logged `phase_end` + `close` + `reconnect` exactly as
   it did at 20:11–20:28. It logged nothing while business frames were dead, so
   the pong path was alive and independent of the business path. **That
   absence is the proof of masking.** Liveness was gated on a frame whose
   answer never leaves the edge.

So the plugin had **zero** end-to-end liveness detection. Only a real business
frame exchange — which needs client activity — could have revealed the death,
and no client happened to talk during the window.

## Design

A second, non-business heartbeat that only the relay *process* can answer.

| frame | direction | fields | relay behaviour |
|---|---|---|---|
| `hb` | agent → relay | `id` (`hb-<n>`, n per connection) | acked by the DO / relay-node process itself; never forwarded; never stamps `agentLastSeen`; hosted relay: no rate-limit token |
| `hb_ack` | relay → agent | `id` echoed verbatim | consumed by the plugin's reader, never dispatched to `on_frame` |

- `relay-cf`: after envelope validation and *before* the token bucket, an `hb`
  from the slot holder is answered with `{"t":"hb_ack","id":…}`; an `hb` from a
  parked/superseded socket is dropped silently (no ack, no error, no stamp) so
  a stale generation notices the misses, reconnects, re-hellos and is told
  4000. The `ping` branch and the `agentLastSeen` stamping rule are untouched.
- `relay-node` (lockstep, not optional): the local dev relay — and every local
  e2e run — acks `hb` the same way; `handleClient` drops an `hb` from a client
  so it is never forwarded to the agent (relay-cf drops it by the same rule).
- `plugin/relay_client.py`: the app-level ping loop is replaced by the beat.
  `ping_interval` (15 s) / `pong_timeout` (10 s) keep their names and now drive
  `hb`; `hb_max_missed = 2`. A missed beat logs `hb_miss` and retries after 2 s;
  the second consecutive miss closes the socket, which is an ordinary phase end
  — the run loop reconnects with backoff exactly as it does for a 1006. The
  counter/missed state resets on connect. `ping_interval=None` disables the
  beat (control runs). Successful beats are not logged (no spam).
  M7.1/M7.2 semantics are untouched: close 4000 fatal, generation gating,
  supervisor, bounded sends, `_tx_lock`.

Detection window in production: a beat every 15 s, a 10 s ack window, one 2 s
retry, then close and up to 1 s of backoff — roughly 22–37 s from tunnel death
to a fresh `hello`, versus never before.

## Reproduction (tests/repro_m73.py) and tests (plugin/tests/test_m73.py)

The harness relay is deliberately the exact incident shape: it answers
`{"t":"ping"}` with `pong`, answers WebSocket pings (the `websockets` protocol
does that), holds the socket open, never acks `hb`, never forwards. Three
clients are pointed at it: the client extracted from a pre-M7.3 revision
(`git show <rev>:plugin/relay_client.py`), the fixed client with the beat
disabled, and the fixed client with a fast beat.

Evidence table — **coordinator-run** (the coding session had no shell, so
these numbers are the coordinator's independent re-runs, not the coder's
claims):

| scenario | old client | fixed, beat disabled | fixed client |
|---|---|---|---|
| silent blackhole (pings answered, `hb` never acked) | NOT RECOVERED in 20 s (39 pings answered, 0 beats) | NOT RECOVERED in 20 s | RECOVERED in 5.0 s (2 misses → close → reconnect) |
| healthy relay (`hb_ack` echoed, frames forwarded) | n/a | no 2nd hello (hold) | no 2nd hello, business round-trip OK |
| close 4000 after hello | fatal | fatal | fatal, no 2nd hello |
| `hb_ack` with a wrong id | n/a | n/a | RECOVERED (misses accumulate; `hb_miss` + `phase_end` logged) |

`plugin/tests/test_m73.py` pins the same four shapes (A, A′, A″ masking probe,
B, C, D) without pytest.

## Residual risks

- Detection is end-to-end only for the agent ↔ relay leg. A DO → browser
  problem is still invisible to the plugin (the SPA has its own ping/close
  logic and the relay's `ready`/`peer` frames).
- Cloudflare's edge could, in principle, terminate `hb` too — it will not
  today, because only exact-string pairs installed with
  `setWebSocketAutoResponse` are auto-answered and `hb` carries a varying `id`.
  If someone adds an `hb` auto-response for wake-up avoidance, this milestone's
  guarantee silently disappears. Do not.
- Worst-case detection is ~37 s, longer than the M7.2 noisy-death path (a RST
  is immediate). That is the price of surviving edge-masked pings.
- The heartbeat does not repair anything by itself: recovery still depends on
  the reconnect path (M7.1/M7.2), which is why those semantics were kept
  byte-for-byte.
