## Source-notes answers (`docs/source-notes.md`, full evidence there)

1. **Delta semantics — raw event incremental, hook cumulative.**
   In `base.py:_on_stream_content_delta`, `event.text` is the new chunk
   only and BaseChannel appends it to its own buffer
   (`streaming_buffers[t] = streaming_buffers.get(t,"") + delta_text`);
   `on_streaming_delta` is then called with the **whole buffer** as
   `accumulated_text` (its docstring: "contains all text received so far
   for this stream_type, including the current delta"). Consequence for
   M1: a plugin that wants true per-delta `evt` frames must diff
   `accumulated_text` against the previous length per (chat, stream_type);
   a consumer of the hook must replace, not append. The in-flight flush
   guard can also coalesce flushes, which is lossless only under the
   cumulative reading.
2. **agent_id — not a channel routing dimension.** A channel instance is
   bound to one workspace (`self._workspace.agent_id`; ChannelManager does
   `load_agent_config(self._workspace.agent_id)`), and
   `build_agent_request_from_user_content` builds `AgentRequest(session_id,
   user_id, input, channel)` with no agent field. Multi-agent selection
   lives at the HTTP layer (`app/agent_context.py:get_agent_for_request`:
   explicit arg → `request.state.agent_id` → `X-Agent-Id` header →
   active agent). Frames *may* carry `agent_id` informationally, but
   nothing routes by it: multi-agent = one plugin instance per agent
   workspace, each dialling the relay with its own `hello{agent}`;
   the plugin's localhost HTTP calls must send `X-Agent-Id: <bound agent>`.
3. **File rule (v1):** total `msg` frame ≤256 KB (≈180 KB raw file after
   base64); larger → `E_TOOBIG`; chunked `file` frames are v2.

## Deviations / known issues

- **Chunk 2 oc_prompt outcome was `None`, not `succeeded`**: the driver
  hit its 1200 s timeout while polling, even though the session had
  completed the work (files all present). No fix-up prompt was sent
  because independent verification (SPA build + mock behaviour in e2e)
  passed; spending another session re-checking working code was not
  warranted. Chunk 1 reported `succeeded` normally (tokens: 148,486 in /
  17,296 out).
- **30 frames/s/tenant rate limit** is specified in `protocol/frames.md`
  but **not enforced** by relay-node (documented there as a local-dev
  simplification; to be enforced in relay-cf / M3).
- **Mock frame order**: mock sends `end` *before* the final
  `msg{parts[]}` frame, so a consumer that finalises strictly on `end`
  sees the complete-message frame one step later. Harmless for the SPA
  (it appends the final message on arrival) but worth aligning with the
  real plugin in M1 (suggest: final `msg` then `end`, or document that
  `end` only closes the stream segment).
- Environment quirk found by OpenCode and confirmed in its README note:
  this VM sets `NODE_USE_ENV_PROXY=1`, which hijacks Node HTTP to
  localhost; the relay smoke test uses a raw TCP socket for `/health`
  and local curl needs `--noproxy '*'`.
- SPA is a skeleton as specced: plain-text rendering (pre-wrap), no
  markdown lib, single chat `default`, no agent switcher UI yet (M4 /
  §13.6 items are later milestones).
