# M7.2 findings — the silent-tunnel zombie: root cause, the named holes, evidence

## The incident (hosted, 2026-10-27)

The M7.1 build passed two full model-switch + chat cycles at 17:18–17:19 CST and
still answered app-side model queries at 17:21 and 17:27. Then the channel went
fully silent: the SPA showed the socket live and the agent online, but no
`status` frame arrived, the models list came back empty, and chat messages were
never processed (nothing reached the Turso archive either). The QwenPaw app
process never restarted (same PID as the 17:14 platform restart), logged zero
errors, and its localhost API still answered instantly at 17:41. Pre-restart
socket evidence from `/proc/<pid>/net/tcp`: the app's connection to the
platform egress proxy (`:1080`) sat in **CLOSE_WAIT with 1 unread byte** — the
proxy side had closed the tunnel and the local side never reaped it. A platform
restart restored service, as always.

The relay WSS runs through that proxy CONNECT tunnel. When the tunnel dies,
the only thing that can bring the channel back is the plugin's own reconnect
logic. It never fired.

## Why the old client could not recover — the named holes

The old `plugin/relay_client.py` ran each connection as: `_run()` awaits
`_reader(ws)`; writer and heartbeat are sibling tasks awaited only in the
`finally` after the reader returns; the reconnect branch sits after that
await. Five concrete defects made a zombie state reachable:

- **H1 (the zombie-maker).** `_reader` awaited the frame callback **inline**
  (`_dispatch` → the channel's handlers). `_run` could only reach its
  reconnect branch after `_reader` returned, and the heartbeat's only remedy
  — `ws.close()` — does **not** cancel a reader parked inside a callback
  await: the close handshake itself needs inbound frames to be read. A parked
  or never-returning dispatch therefore froze the client forever in a
  "connected" state: no exception, no close code, no reconnect, nothing in
  any log. The **1 unread byte** in the incident socket fits exactly: a frame
  (plausibly the close echo, or the frame that would have unblocked things)
  arrived while nobody was in `recv()`.
- **H2.** Writer and heartbeat failures were invisible while the reader
  lived: both were awaited only in `_run`'s `finally`, after the reader had
  already returned. A dead writer meant the client could receive forever and
  never send again, with nothing noticing.
- **H3.** `_send_direct` called `ws.send()` with **no timeout**, serialized
  behind `_tx_lock`. One send stuck on a dead tunnel wedged every sender
  behind it — including the heartbeat's own ping.
- **H4.** `websockets.connect` ran with `ping_interval=None`: no
  transport-level dead-peer detection at all. The app-level heartbeat's pong
  is consumed by the (possibly parked) reader, so the heartbeat measured the
  reader's liveness, not the tunnel's.
- **H5.** No supervisor: `_run` was a single fire-and-forget task. Any exit
  path that wasn't the two known ones (explicit stop, fatal 4000) ended the
  client silently — `WebChannel.start()` is never called again by anyone.

Which exact callback parked in the hosted incident cannot be proven post-hoc —
the plugin's loggers never reached `qwenpaw.log`, so the failure left no trace
anywhere (that observability gap is itself fixed in this milestone). Every
channel-side await sampled during the audit is an httpx call with an explicit
10 s timeout, and `_handle_msg`'s enqueue is synchronous. The structural hole
does not depend on identifying the callback: **any** sufficiently slow or
stuck dispatch froze the connection permanently, and the reproduction below
proves it.

## Reproduction (tests/repro_m72.py, raw RelayClient harness)

Three server-side kill shapes, run against the pre-M7.2 client (extracted
from git HEAD) and against the fixed client. "Recovered" = a second hello
from the same client session within the deadline.

| scenario | old client | fixed client |
|---|---|---|
| transport destroyed (no close frame) | recovered in 1.0 s | recovered in 1.0 s |
| half-close: server pauses reading, stays silent | recovered in 7.0 s | recovered in 7.0 s |
| **parked frame callback** (server never answers the app-level ping) | **NOT RECOVERED** (no 2nd hello in 20 s) | **recovered in 2.0 s** |

Destroy and silence already recovered in the old code — its reader was sitting
in `recv()`, so the failure surfaced as an exception and the reconnect branch
ran (silence only via the WebSocket-level close timeout, hence 7 s). The
incident's shape was the third one: something in the dispatch path stopped
returning, the reader never went back to `recv()`, and every safety mechanism
the old code had was downstream of that await.

## The fix

`plugin/relay_client.py` was restructured around one invariant: **a connection
phase ends when the first of {reader, writer, heartbeat} ends, and the run
loop always decides what happens next.**

- The three per-connection tasks race under `asyncio.wait(FIRST_COMPLETED)`;
  the phase log records which task ended and why. Remaining tasks are
  cancelled with a bounded 5 s cleanup (`_cancel_phase_tasks`), so a parked
  callback is cancelled, not waited on (closes H1, H2).
- A supervisor (`_supervise`) wraps the run loop: any exit that is neither an
  explicit stop nor the fatal superseded-close restarts the loop after a
  short delay, including `BaseException` escapes (closes H5).
- `websockets.connect` now gets explicit `ping_interval=20` /
  `ping_timeout=20`: a silent tunnel is detected at the transport layer in
  bounded time regardless of dispatch state (closes H4).
- Every send is wrapped in `asyncio.wait_for(..., send_timeout=10 s)` (closes
  H3).
- M7.1 semantics preserved: close 4000 is still fatal, and `client._task`
  still finishes on it. One refinement found in this milestone's own live
  logs: a phase once ended via the **writer** holding a `ConnectionClosedError`
  with code 4000 while `_close_code` was still `None` (only the reader
  recorded it), briefly taking the transient path until the workspace stop
  landed. Senders now record the close code too (`_note_close_code` in the
  writer and heartbeat), and the relay's generation gate remains as a
  backstop. Pinned by test scenario G.

## Diagnostics: the plugin file log (plugin/filelog.py)

Plugin module loggers do not reach `qwenpaw.log` (established in M3), which is
why the incident left no trace. The plugin now keeps its own tiny log,
`webchannel.log` in the agent workspace directory: `channel_start`,
per-connection `connect` / `hello` / `phase_end` (which task ended, detail) /
`close code=` / `reconnect delay=` / `fatal` / `supervisor_restart` /
`loop_exit` / `stopped` events with millisecond timestamps. `FileLog` rotates
at 256 KB with two backups and its `write()` never raises — logging can never
break the channel. In the local stack it recorded the full M7.1 switch
choreography (each superseded instance: `phase_end reader`, `close
code=4000`, `fatal`, `stopped`) and every e2e_m72 kill cycle (`close
code=1006`, `reconnect delay=1.0`, fresh `hello`).

## Relay side: `agentLastSeen` (relay-cf)

The relay previously had the same blindness from the other side: the DO kept
reporting the agent online because the socket attachment said so. `GET
/health` now also returns `agentLastSeen` — the DO's wall-clock time of the
agent socket's last **business** frame (hello stamps it too). The app-level
`ping` deliberately does **not** stamp it: Cloudflare answers that via
`setWebSocketAutoResponse` without waking the DO, and a tunnel kept warm by
auto-pongs is precisely the zombie shape we need to see through. From outside,
the silence signature is now: `agentOnline: true` with an `agentLastSeen`
that stops advancing. (Right after a deploy the field reads `null` until the
agent's next business frame — the DO state starts empty and an idle agent
sends none.)

## Residual risks / notes

- The hosted trigger (which dispatch parked, if any) stays unproven; the next
  tunnel death on the hosted instance will now leave `phase_end` evidence in
  the workspace `webchannel.log` and a frozen `agentLastSeen` on `/health`.
- Recovered-from-silence still takes seconds, not milliseconds: detection is
  bounded by the keepalive cadence (ws ping 20 s + timeout 20 s worst case in
  production settings; the app-level heartbeat usually fires first).
- Buffered outbound frames survive reconnects (bounded deque, oldest dropped
  past 200); frames queued during an outage are flushed onto the new socket.
