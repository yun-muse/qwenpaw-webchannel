### What actually happened with OpenCode (important operational lesson)

- `tools/oc_prompt.py`'s completion detection is **unreliable**: it
  declared the first m1-plugin session "succeeded" with a detailed
  completion report while that session was in fact still running
  (research phase, 71 shell reads of the reference source) and had
  written nothing. Ground truth is the server API
  (`GET /api/session/active`, message tool-call tallies) plus `ls` on
  disk — not the driver's verdict and not the model's prose. The repo
  AGENTS.md already carries the same warning from the project side.
- The first session did eventually write `relay_client.py` (after a
  "stop researching, write now" nudge via the session prompt endpoint),
  then ended having made 73 shell calls and exactly 1 write.
- The fix-up chunks for util/frames/tests landed (via layered sessions)
  and pass; the final chunk (channel.py + plugin.py + plugin.json +
  README) was attempted with glm-5.3-flash-free and then
  deepseek-v4.1-flash-free and **both failed instantly with 0 tokens**.
  The OpenCode server log gives the reason verbatim:
  `Failed to drain Session — AI.Error: Free usage limit reached. Free
  models work in OpenCode (https://opencode.ai); subscribe to OpenCode
  Go…` — the anonymous free quota for this egress identity is
  exhausted. Further generation attempts are futile until it resets
  (no reset time is published; third-party sources suggest a daily
  window).

### Environment fix required (document, don't rediscover)

The first app start inherited the VM's `NO_PROXY`, which contains
bracketed IPv6 entries (`[::1]`, `[fd8b:…::1]`). The OpenAI client's
httpx `URLPattern` construction chokes on them —
`httpx.InvalidURL: Invalid port: ':1]'` — and every chat failed
instantly. Restarting the app with `NO_PROXY=localhost,127.0.0.1,::1`
(keeping the egress `http(s)_proxy`) fixed it: agent builds and chats
start. The same error had appeared earlier as a kilo discovery warning.

### Keyless model: configured, but completions hang from this VM

- As predicted from `provider_manager.py:_initialize_free_models`, the
  first app start auto-enabled Kilo and set the active model:
  `GET /api/models/active` →
  `{"active_llm": {"provider_id": "kilo", "model": "kilo-auto/free"},
  "effective_max_input_length": 256000}`. No API key was copied from
  anywhere; none exists locally.
- But the model does not answer from this VM:
  - In-app probe (`POST /api/console/chat`, "Say hello in one short
    sentence"): agent built (`builder: built agent … model=kilo/
    kilo-auto/free`), chat stuck in status `running` for 20+ minutes,
    zero output events after the initial `in_progress`.
  - Direct probe: `GET https://api.kilo.ai/api/gateway/models` → 200
    in 2.7 s (gateway reachable), but `POST …/chat/completions` with
    `kilo-auto/free` → no response in 45 s; with `openrouter/free` and
    an `X-KiloCode-TaskId` header → no response in 30 s (curl code 000
    both times).
- Conclusion: keyless completions via the Kilo gateway are not usable
  from this VM right now (listings yes, completions hang). Whether the
  hosted instance works because of its different egress or another
  entitlement is out of scope here; no keys were taken from it.
