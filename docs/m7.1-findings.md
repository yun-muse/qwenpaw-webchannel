# M7.1 findings — channel silence after a model-switch reload

## Symptom (hosted, deterministic)

After a model switch via the M7 `set_model` flow, the switch itself
lands (`model_changed` + `status` reach the SPA, app config updated),
but once the app's hot reload finishes, the channel is silent: `models`
requests and chat messages get no response while the relay still
reports the agent online. A full app restart restores service — until
the next switch.

## How a reload actually interleaves (pinned from app source)

`PUT /api/models/active` (scope=agent) calls
`schedule_agent_reload` → `MultiAgentManager.reload_agent`
(qwenpaw-ref `src/qwenpaw/app/multi_agent_manager.py`):

1. A NEW workspace instance is created and **fully started first**
   (zero-downtime): its WebChannel builds a NEW RelayClient, which
   connects to the relay; the relay closes the OLD socket with code
   4000 ("replaced by new agent connection") and takes the new one.
2. The instances are swapped atomically.
3. Only then is the old instance stopped — immediately when it has no
   active tasks, otherwise via a **delayed cleanup** that waits for
   the old workspace's tasks in 60 s rounds for up to **24 hours**
   before forcing `old_instance.stop()`.

So there is always a window — milliseconds on a fast idle box, seconds
on the loaded hosted container (~6 s between "Reloading agent" and
"Old workspace instance stopped" there), potentially far longer on
the delayed-cleanup path — in which the OLD RelayClient has been
evicted (4000) but its `stop()` has not run. Its reconnect loop is
still armed, with the backoff reset to **1 s** by its last successful
connect.

## Root cause: the evicted old client reconnects — a replacement war

`RelayClient._run` treated a 4000 close like any transient drop: wait
out the backoff, reconnect. The relay (both implementations) granted
the slot to whichever agent socket connected last and evicted the
previous one with 4000. Two live RelayClients in one app process
therefore evict each other in turn:

**Reproduced locally.** relay-node with connection logging + the
local app, with the installed plugin copy's `WebChannel.stop()`
artificially delayed by 6 s (diagnostic patch to the installed copy
only, simulating the hosted stop latency; product code untouched).
Six `set_model` half-cycles produced **42 agent connections**: after
every switch, an `AGENT CONNECT` lands every ~1.0 s (the shared
initial backoff), each closing the incumbent with 4000 — 36 closes
with code 4000 in total. The war ends only when the delayed `stop()`
finally runs: the then-current socket closes with **1000**
(client-initiated, `wasCurrent=true`) and the survivor reconnects
into the empty slot ~0.5 s later. Without the artificial delay the
local stop lands ~0.1–0.3 s after the swap, wins the race against
the 1 s backoff, and nothing is visible — which is why the plain
local stack never showed the bug, and why the M7 e2e (which re-sends
`models` until answered) masked it completely.

During the war, roughly half of all client→agent frames land on the
OLD channel instance: its `msg` handler enqueues into a stopped
workspace (no reply ever), and the SPA's requests appear to vanish.
On the hosted instance the war's end-state is a permanently wrong
holder rather than self-healing: the old workspace's stop goes
through the slow/delayed path, and the CF relay adds a failure mode
relay-node cannot reproduce — after a hibernation wake, the DO
rebuilt `this.agent` from `getWebSockets()` with "last one wins", so
the slot could be bound to a stale socket whose reader no longer
exists while `/health` still reported `agentOnline: true`. (The
exact hosted interleaving cannot be replayed locally — workerd dev
does not hibernate like production — but every variant shares the
same root: **an evicted, superseded client was allowed to reconnect
and take the slot back**. The fix removes that root in both layers,
so the end-state is correct by construction rather than by race.)

## Refuted candidates

- **Archiver stop breaking `WebChannel.stop()`**: `TursoArchiver.stop()`
  is fully guarded (never raises, ≤5 s wait), so `relay.stop()` is
  always reached when the channel stop runs at all.
- **`RelayClient.stop()` semantics**: cancel + close is correct — the
  problem is purely that it can arrive after the 1 s backoff fires.
- **The new channel not starting after reload**: disproved locally —
  the new instance connects and wins the slot within ~1 s of the PUT
  (relay log), and its `status` push reaches clients.
- **E_AUTH fatal**: neither relay ever sends an `E_AUTH` frame; the
  plugin's fatal path was not involved.

## The fix

Generation-gated agent slot (protocol/frames.md §3):

- **Plugin** (`relay_client.py`): each RelayClient has a `session`
  (uuid) and `started` (construction time, wall-clock µs — exactly
  representable in a JS double), sent in `hello`. The reader records
  the close code; a close with **4000 now sets `_fatal`** — "superseded
  by a newer instance; not reconnecting" — so an evicted client dies
  immediately instead of waiting for `stop()`. Transient closes
  (1000/1001/1011, network errors) still reconnect with backoff, and
  a re-hello/reconnect of the same client keeps its generation.
- **Relays** (relay-node + relay-cf, semantics in lockstep): a new
  agent socket is *parked* — upgrade-time eviction is gone. The slot
  is won at `hello`: an incoming `started` **older** than the
  holder's closes the newcomer with 4000 ("superseded") and leaves
  the holder untouched; a newer-or-equal hello takes the slot
  (previous socket closed 4000, then `peer` + outbox flush + `ready`).
  Frames from parked/superseded sockets are never forwarded. Legacy
  hellos without `started` count as generation 0.
- **relay-cf hibernation**: the winner's `{won, started, session}` is
  stored in the socket attachment; the constructor rebuild picks the
  greatest-`started` winner (legacy = won, generation 0) instead of
  blindly taking the last socket, and restores `agentMeta` from it.

The SPA needed no change: with the slot stable, its existing
re-request-on-open behaviour is sufficient — the silence was never a
client-side request bug (evidence: raw protocol probes went equally
unanswered).

  exactly **6 agent connections for 6 switches**, strictly increasing

  GENERATION group (stale hello → closed 4000, `/health` still
  `agentOnline: true`, probe frame still delivered to the holder).

## Rollout ordering (matters)

Deploy **relay-cf before** installing the new plugin on the hosted
instance. With an old relay + new plugin, a zombie eviction would
close the live client with 4000 and the new fatal rule would keep it
down until its workspace restarts. With the new relay + old plugin,
behaviour is no worse than today (legacy generation 0; the war is
still possible until the plugin lands) — so relay first, plugin
second, and no model switches in between.
